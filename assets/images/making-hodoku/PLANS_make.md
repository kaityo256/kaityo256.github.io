# Hodoku 問題生成計画

## 1. 目的

`maker/` 以下に、Hodoku の問題を自動生成する C++ プログラムを実装する。

入力として偶数サイズの正方格子、乱数シード、生成問題数を YAML で受け取り、各問題について以下を生成する。

- 格子グラフ上のハミルトンサイクル
- 一意解を保証する固定宝石集合
- 生成条件を含む JSON ファイル

問題生成器は1プロセス内ではシリアルに動作する。多数生成時の並列化は外部で複数プロセスを起動して行うため、本実装では並列化を行わない。

## 2. 対象ディレクトリ

原則として `maker/` 以下のみを変更する。

推奨構成:

```text
maker/
├── CMakeLists.txt
├── src/
│   ├── main.cpp
│   ├── config.cpp
│   ├── cycle_generator.cpp
│   ├── uniqueness_solver.cpp
│   ├── fixed_selector.cpp
│   └── output.cpp
├── include/
│   ├── config.hpp
│   ├── puzzle.hpp
│   ├── cycle_generator.hpp
│   ├── uniqueness_solver.hpp
│   ├── fixed_selector.hpp
│   └── output.hpp
├── third_party/
├── config/
│   └── example.yaml
└── output/
    ├── 6x6/
    ├── 8x8/
    └── 10x10/
```

ファイル分割は必要に応じて調整してよいが、以下の責務は分離する。

- 設定読み込み
- ハミルトンサイクル生成
- 一意性判定
- 固定宝石選択
- JSON 出力

## 3. ビルド方針

- C++17 以上を使用する。
- ビルドには CMake を使用する。
- 問題生成器本体は標準 C++ を基本とし、外部依存を最小限にする。
- 現在は外部依存を持たず、必須3項目のスカラー形式に限定した YAML 読取器を使用する。
- 読取器は未知キー、重複キー、必須キーの欠落、不正な整数値を拒否する。
- 将来、YAML の入れ子や配列が必要になった場合は、single-header / header-only の `fkYAML` を第一候補として導入する。
- JSON 出力は単純な構造なので、不要に大きな JSON ライブラリへ依存しない。必要であれば小規模な出力関数を自前実装してよい。

## 4. YAML 入力仕様

問題生成器は YAML 設定ファイルのパスをコマンドライン引数として受け取る。

例:

```bash
./hodoku_maker config/example.yaml
```

YAML の必須項目:

```yaml
size: 6
seed: 12345678
count: 100
```

各項目の意味:

- `size`
  - 実際の格子幅。
  - `size x size` の正方格子を生成する。
  - 2以上の偶数のみ許可する。
- `seed`
  - このプロセスの基準乱数シード。
  - 64 bit 符号なし整数として扱うことを推奨する。
- `count`
  - このプロセスが生成する問題数。
  - 問題番号 `index` は `0` から `count - 1` とする。

不正な設定値の場合は、分かりやすいエラーメッセージを標準エラーへ出力し、非0終了コードで終了する。

## 5. 乱数と再現性

同じ YAML 入力から同じ問題群を再生成できることを要求する。

基準乱数シード `seed` と問題番号 `index` から、各問題専用の乱数シード `problem_seed` を決定する。

単一の乱数生成器を問題間で連続使用するのではなく、各問題が独立した seed を持つ構造を推奨する。

理由:

- ある問題の生成途中で再試行回数が変わっても、後続問題への影響を小さくできる。
- 特定問題だけを再現しやすい。
- 外部での自明並列と相性がよい。

`problem_seed` の導出には、`seed` と `index` を入力とする決定的な 64 bit mixing 関数を使用する。`splitmix64` 相当の単純な整数 mixing でよい。

JSON には少なくとも基準 `seed` と `index` を保存する。必要であれば `problem_seed` も保存してよい。

乱数生成器には `std::mt19937_64` を使用してよい。

## 6. 基本データモデル

格子サイズを `W = size` とする。

格子点数:

`M = W * W`

格子点IDは row-major order で定義する。

`id = y * W + x`

正解配置では、宝石IDと格子点IDを一致させる。

`solution_position[jewel_id] = jewel_id`

各宝石はハミルトンサイクル上で前後の2宝石と接続する。

JSON 上では個々の `prev` / `next` は保存せず、`cycle` 配列から導出する。

`cycle[i]` の接続相手は以下とする。

- `cycle[(i - 1 + M) % M]`
- `cycle[(i + 1) % M]`

## 7. ハミルトンサイクル生成

### 7.1 基本方針

`W` は偶数なので、`W = 2N` とする。

`2N x 2N` の細格子を `2x2` ブロックに分割し、`N x N` の粗格子を考える。

以下の手順で必ずハミルトンサイクルを生成する。

1. 粗格子 `N x N` 上にランダムな全域木を生成する。
2. 各 `2x2` ブロック内に4頂点の小サイクルを作る。
3. 粗格子の全域木の各辺について、対応する隣接 `2x2` ブロックの小サイクルを局所的に接続する。
4. 全域木の `N^2 - 1` 辺をすべて処理すると、全細格子点を含む1本のハミルトンサイクルになる。

### 7.2 ランダム全域木

初期実装では randomized DFS を採用する。

手順:

1. 粗格子の開始頂点を乱数で選ぶ、または固定してよい。
2. 未訪問の上下左右隣接頂点を列挙する。
3. 候補順を乱数で shuffle する。
4. DFS で訪問し、採用した辺を全域木へ追加する。

randomized DFS が生成する全域木は一様分布ではないが、Hodoku の問題生成用途では許容する。

将来、生成される閉路形状の偏りが問題になった場合は Wilson 法等への置換を検討する。

### 7.3 `2x2` 小サイクルの統合

各 `2x2` ブロックでは、4頂点を囲む4-cycleを初期状態とする。

粗格子で左右に隣接する2ブロックを統合する場合:

- 境界に接する2本の縦辺を削除する。
- ブロック間を結ぶ2本の横辺を追加する。

上下に隣接する場合は、その90度回転版を行う。

この操作により、2つの独立したサイクルが1つに統合され、各頂点の次数2は保たれる。

全域木の各辺は異なる連結成分を統合するため、最終的に全頂点を含む単一サイクルとなる。

### 7.4 `cycle` 配列への変換

生成後のグラフでは各頂点の次数がちょうど2である。

任意の頂点、原則として頂点 `0` から開始し、直前の頂点ではない方の隣接頂点を順にたどることで、全頂点を1周する `cycle` 配列を生成する。

出力前に以下を検証する。

- `cycle.size() == M`
- 全IDが一度ずつ現れる。
- `cycle[i]` と `cycle[(i+1)%M]` が上下左右の隣接格子点である。

## 8. 一意性判定

### 8.1 一意性の定義

固定宝石を指定した状態で、すべてのボンドが上下左右の隣接格子点を結ぶような宝石配置が、正解配置ただ1つだけ存在することを要求する。

色は一意性判定に使用しない。

### 8.2 問題の定式化

候補解では各宝石 `j` に格子点 `pos[j]` を割り当てる。

制約:

1. すべての宝石が異なる格子点を占める。
2. 固定宝石は `pos[j] = j` を満たす。
3. `cycle[i]` と `cycle[(i+1)%M]` の配置先は上下左右に隣接する。

既知の正解配置は `pos[j] = j` である。

一意性判定では全解を数えない。

「既知の正解とは異なる合法配置が1個でも存在するか」を探索する。

- 別解が見つかった時点で `ALTERNATIVE_FOUND` として即時終了する。
- 探索空間を尽くして別解がなければ `UNIQUE` とする。

### 8.3 DFS 探索

基本探索はハミルトンサイクル順の DFS / backtracking とする。

`cycle[0], cycle[1], ..., cycle[M-1]` の順に宝石を配置する。

現在の宝石の配置位置が決まっている場合、次の宝石の候補位置は現在位置の上下左右の最大4点のみである。

候補条件:

- 格子内である。
- 未使用位置である。
- 固定宝石なら正解位置と一致する。
- 他の固定宝石専用位置を可動宝石が使用しない。

最後の宝石を置いたら、最初の宝石との隣接を確認する。

### 8.4 正解とは異なる解の検出

探索状態に `differs_from_solution` 相当のフラグを持つ。

宝石 `j` を `j` 以外の格子点へ置いた時点で true とする。

完成配置が得られた場合:

- false なら既知の正解なので無視して探索継続。
- true なら別解なので即時終了。

### 8.5 候補順

別解を早く発見するため、正解位置以外の候補を先に試し、正解位置を最後に試す。

非一意な固定集合に対する判定を高速化することを優先する。

### 8.6 枝刈り

以下を実装する。

#### 固定位置制約

固定宝石は正解位置以外へ置けない。

また固定宝石用の位置は、他の宝石が使用できない。

#### Manhattan 距離と parity

現在位置から、サイクル上で次に現れる固定宝石まで `k` ステップ残っているとする。

現在位置と固定位置の Manhattan 距離を `d` としたとき、最低限以下が必要である。

- `d <= k`
- `d % 2 == k % 2`

満たさない場合は即座に backtrack する。

必要に応じて、前方だけでなく逆方向側の固定石も利用してよい。

#### 残り領域の連結性

配置済み経路によって未使用格子点が到達不能な複数領域へ分断された場合、その枝ではハミルトンサイクルを完成できない。

BFS / flood fill で残り領域の連結性を確認し、分断されていれば枝を切る。

格子点数は主に最大100程度を想定しているため、単純な BFS を基本とする。

#### 低次数・行き止まり

未使用格子点について、将来サイクルへ組み込むための利用可能な隣接点が不足した場合は枝を切る。

現在の探索端点や最後に閉じる始点の扱いに注意し、誤った枝刈りをしないこと。

まず安全に正しさを保証できる条件のみ実装し、必要に応じて強化する。

## 9. 固定宝石の選択

### 9.1 基本戦略

初期固定集合を空集合とする。

```text
fixed = {}
```

以下を繰り返す。

1. 現在の `fixed` で別解探索を行う。
2. 別解がなければ一意なので終了する。
3. 別解と正解配置を比較する。
4. 位置が異なる宝石の集合 `D` を求める。
5. `D` から1個選び `fixed` へ追加する。

追加する宝石は、少なくとも発見済みの別解を必ず排除する。

### 9.2 固定宝石の選び方

初期実装では `D` から乱数で1個選んでよい。

将来、固定石数や難易度を改善したい場合は以下のヒューリスティックを検討できる。

- 過去に見つかった複数別解を多く同時に排除する宝石を優先する。
- 候補固定石ごとに簡易評価を行う。
- 盤面上で固定石が極端に偏らないようにする。

最初の実装では最適化を行わない。

## 10. 冗長な固定宝石の削減

一意解が得られた後、固定石数を削減する。

手順:

1. `fixed` の順序を乱数で shuffle する。
2. 各固定宝石 `j` を1個ずつ一時的に除く。
3. 一意性判定を行う。
4. 除いても `UNIQUE` なら、その宝石は削除したままにする。
5. `ALTERNATIVE_FOUND` なら元に戻す。

これにより、少なくともその走査終了時点で各固定石を単独では除去できない局所的な極小集合を得る。

完全な最小固定集合を求める必要はない。

必要であれば固定石削減を複数回 shuffle して繰り返してもよいが、初期実装では1巡でよい。

## 11. 問題生成全体フロー

各 `index` について以下を実行する。

```text
1. seed と index から problem_seed を生成
2. randomized DFS で粗格子の全域木を生成
3. 2x2 小サイクルを全域木に従って統合
4. cycle 配列を生成・検証
5. fixed = {}
6. 別解が存在する間:
     a. 別解を1個取得
     b. 正解と異なる宝石集合 D を作成
     c. D から1個選び fixed に追加
7. fixed の冗長要素を削減
8. 最終一意性を再確認
9. JSON を出力
```

生成途中で内部整合性エラーが起きた場合は、問題番号と seed を含む診断情報を標準エラーへ出力する。

## 12. JSON 出力仕様

各問題を1 JSON ファイルとして出力する。

例:

```json
{
  "version": 1,
  "width": 6,
  "height": 6,
  "seed": 12345678,
  "index": 17,
  "cycle": [0, 1, 2, 8, 14, 13],
  "fixed": [0, 7, 19, 24]
}
```

上記 `cycle` は説明用の省略例であり、実際には `width * height` 個の全頂点IDを含む。

現在の出力には、問題単体の再現と診断を容易にするため `problem_seed` も保存する。

将来、必要に応じて generator version を追加してよい。

ただし Godot 側で不要な内部探索情報は出力しない。

### ファイル名

推奨形式:

`puzzle_<size>x<size>_s<seed>_n<index>.json`

例:

`puzzle_6x6_s12345678_n000017.json`

`index` は固定桁数でゼロ埋めする。少なくとも6桁を推奨する。

同じ `size` と `seed` を同時に複数プロセスで実行した場合はファイル名が衝突するため、外部並列実行側では同一 `(size, seed)` を重複させないことを前提とする。

異なる seed を与えた複数プロセスからの同時出力では衝突しない。

## 13. 出力先

生成器の生出力は `maker/output/<size>x<size>/` に保存する。

例:

```text
maker/output/6x6/puzzle_6x6_s12345678_n000017.json
```

ディレクトリが存在しない場合は作成する。

Godot 側へ採用する問題は、別工程でゲーム用フィールドを付加し、`game/data/puzzles/<size>x<size>/` へ出力する。

問題生成器から直接 `game/` 以下へ書き込まない。

## 14. 検証とテスト

最低限、以下のテストを用意する。

### 設定読み込み

- 正常な YAML を読める。
- 奇数 `size` を拒否する。
- 0以下の `count` を拒否する。
- 不正な seed を拒否する。

### サイクル生成

- 4x4 で全16頂点を1回ずつ通る。
- 6x6 で全36頂点を1回ずつ通る。
- 8x8 で全64頂点を1回ずつ通る。
- 10x10 で全100頂点を1回ずつ通る。
- 全サイクル辺が上下左右隣接である。
- 全頂点の次数が2である。

### 一意性ソルバー

小さい既知例を用意し、以下を確認する。

- 別解がある場合に `ALTERNATIVE_FOUND` を返す。
- 十分な固定石がある場合に `UNIQUE` を返す。
- 正解そのものを別解として誤判定しない。

### 固定石生成

- 出力された `fixed` で一意性が成立する。
- 削減後も一意性が成立する。
- `fixed` の各IDが有効範囲内で重複しない。

### 再現性

同じ YAML から2回生成し、全JSONが一致することを確認する。

## 15. パフォーマンス方針

主対象は `4x4`、`6x6`、`8x8`、`10x10` とする。

ハミルトンサイクル生成は軽量であり、主な計算コストは一意性判定にあると想定する。

まず正しさを優先した DFS + 枝刈りを実装する。

8x8または10x10で一意性証明が重い場合は、プロファイル結果に基づき以下を検討する。

- より強い連結性枝刈り
- forced move の伝播
- 未使用頂点の次数制約強化
- 固定石までの双方向距離制約
- 探索順の改善
- 探索状態のメモ化

SAT / ILP / 外部ソルバーは初期実装では使用しない。

## 16. Codex 実装時の優先順位

以下の順に実装する。

1. CMake と最小 CLI
2. YAML 設定読み込み
3. 基本データ構造
4. randomized DFS による粗格子全域木
5. ハミルトンサイクル生成
6. cycle 検証
7. 一意性 DFS の最小実装
8. 固定位置・距離・parity の枝刈り
9. 連結性枝刈り
10. 固定宝石追加
11. 固定宝石削減
12. JSON 出力
13. 再現性・ユニットテスト
14. 必要に応じた性能改善

各段階でテストを通し、正しさが確認できてから次へ進む。

## 17. 実装結果

### 17.1 実装済みコンポーネント

2026年8月12日時点で、初期実装の優先順位1〜13は完了している。

```text
maker/
├── CMakeLists.txt
├── README.md
├── config/example.yaml
├── include/
├── src/
├── tests/tests.cpp
├── make_seed.py
└── check_equivalent.py
```

責務は以下の単位に分離している。

- `config`: YAML 設定読取と入力検証
- `cycle_generator`: seed 導出、サイクル生成、サイクル検証
- `uniqueness_solver`: 別解探索と枝刈り
- `fixed_selector`: 固定宝石の追加と削減
- `output`: JSON 直列化、出力パス生成、ファイル書き込み
- `main`: CLI と問題ごとの生成フロー

JSON は一時ファイルへ書き込んだ後に rename し、不完全なファイルを最終ファイル名で残しにくい構造とした。

### 17.2 ビルドと実行

```bash
cmake -S maker -B maker/build -G Ninja -DCMAKE_BUILD_TYPE=Release
cmake --build maker/build
ctest --test-dir maker/build --output-on-failure
./maker/build/hodoku_maker maker/config/example.yaml
```

生成物は `maker/output/<size>x<size>/` に書き込む。`maker/build/`、生成 JSON、バッチ生成用 YAML、シェルスクリプト、Python キャッシュは `.gitignore` で除外する。

`maker/make_seed.py` は、複数 seed の YAML と外部シリアル実行用 `task.sh` を作る補助スクリプトである。生成器本体は計画どおりシリアル実装のままとする。

### 17.3 検証結果

- GCC 13.3.0、CMake / CTest 3.28.3、Ninja 1.11.1 でビルドを確認した。
- 設定読取、2x2〜8x8のサイクル生成、一意性判定、固定宝石選択、JSON について CTest が成功した。
- 同じ YAML を2回実行し、4x4の出力 JSON の SHA-256 が一致することを確認した。
- 基準 seed `12345678` の各1問について、6x6は約0.06秒、8x8は約9秒で生成した。値は開発環境での参考値であり、性能保証値ではない。
- 10x10は異なる seed で14問を実生成済みであり、そのうち10問をゲームに採用している。

### 17.4 ゲーム用ステージへの変換

`game/tools/build_stage_data.py` は `maker/output/` から採用問題を選び、以下のゲーム用フィールドを付加して `game/data/puzzles/` へ出力する。

- ゲーム内で一意な `id`
- 固定宝石を動かさない決定的な `initial`
- 完成絵を参照する `pattern`
- 元問題のファイル、`seed`、`index`、`problem_seed` を保持する `source`

4x4、6x6、8x8、10x10は各10問を採用している。全ステージで `source.temporary_duplicate = false` を記録する。

`game/tools/generate_answers.py` は各ステージの正解配置を宝石、ボンド、固定宝石オーバーレイ付きのPNGとして `game/assets/answer/` へ生成する。同時に、開始位置と巡回方向を無視したハミルトンサイクルの一致を検査する。現行採用データでは6x6、8x8、10x10は各10サイクルすべて異なり、4x4は10問中4種類である。4x4の重複グループは `01/06`、`02/04/05/08/10`、`03/07` で、`09` は単独である。

`game/tools/validate_stage_data.py` で、全40ステージについてサイクルの隣接性、初期配置の置換、固定宝石、パターン参照を検証する。

### 17.5 等価問題の検査

`maker/check_equivalent.py` は、JSON のメタデータを除外し、以下が一致する問題を等価として検出する。

- 正方格子の回転・反転8通りのいずれかで重なる。
- 無向ボンド集合が一致する。
- 固定宝石集合が一致する。
- `cycle` 配列の開始位置と巡回方向の違いは無視する。

実行例:

```bash
python3 maker/check_equivalent.py maker/output/6x6
python3 maker/check_equivalent.py --fail-on-equivalent maker/output/6x6
```

2026年8月12日に6x6の190問を検査した時点では、以下の1組が等価と判定された。

```text
puzzle_6x6_s10_n000009.json
puzzle_6x6_s4_n000005.json
```

前者を反転後に180度回転すると後者に一致し、固定宝石は `[4, 6, 8, 25]` から `[7, 24, 26, 34]` へ対応する。
