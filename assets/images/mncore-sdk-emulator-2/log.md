# MN-Core 2でライフゲームが動くまで

## はじめに

MN-Core SDK 0.7とMN-Core 2 Emulatorを使い、32×32のConway's Game of
Lifeを10世代進めるサンプルを作った。

ライフゲーム自体の規則は単純だ。各セルについて8近傍の生存数を数え、次の
どちらかなら次世代で生存、それ以外なら死亡とする。

- 近傍が3個なら、現在の状態によらず生存する
- 近傍が2個で、現在も生きているなら生存し続ける

CPUなら二重ループの中に条件式を書けば終わる。しかし今回は、32×32の盤面を
MN-Core 2の構造に合わせて分割し、毎世代hostからdeviceへ送り、計算結果を
hostへ戻さなければならない。実装で難しかったのはLifeの規則ではなく、
「どのデータを、どの順序で、どのPEに渡すか」だった。

## 最初に考えた素直な配置

盤面は8×8個のblockに分割し、各blockが4×4セルを担当することにした。
これで64 blockとなり、MN-Core 2の64個のL1Bへ自然に対応する。

4×4セルの次世代を計算するには、その外側の1セルも必要になる。そのためhost側で
周期境界条件を処理し、各blockに6×6のhalo付き入力を作る。論理的な入出力は
次の大きさになる。

```text
入力: 64 block × 6 × 6 = 2304 FP32
出力: 64 block × 4 × 4 = 1024 FP32
```

この時点では、1 blockを1 L1B、block内の各セルを1 MABへ置けば、きれいに
収まるように見えた。haloもhostで完成させるので、device内で隣のL1Bから値を
受け取る必要はない。

## scatter/gatherで最初の壁に当たる

実際にSDKのscatter/gatherへ載せようとすると、論理配列をそのまま2304要素だけ
渡せばよいわけではなかった。明示的scatter/gatherのバッファは、全PEに対する
local slotを並べたSoA形式、つまり次の順序を前提としている。

```text
local slot × NUM_PE + PE番号
```

さらに、device側のベクトル型と各PEのrecordサイズも揃える必要がある。
ここで「論理入力64×6×6」と「SDKへ渡す物理入力」を同じものとして扱う方針を
捨てた。この区別がつくまでが、今回いちばん大きな回り道だった。

解決策は、hostでhalo付きblockを作った後、各セルの計算に必要な情報を自己完結した
PE recordへ展開することだった。1 recordには次を入れる。

- 8近傍の値
- 現在のセル値
- 論理セルID

32×32なので論理セルは1024個ある。各MAB配下には4 PEあるため、同じ論理セルを
4 PEへ複製すると、1024×4で全4096 PEをちょうど使用できる。物理バッファは
大きくなるが、各PEは通信なしで必要な情報をすべて持てる。

この構成では「基本の論理配置は1 block = 1 L1B、1セル = 1 MAB」という見通しを
保ちつつ、SDKの実際の転送単位にも合わせられた。

## 出力順序を信用しないためのセルID

入力をscatterした後、結果が論理セル順で戻ると仮定すると、SDK内部のPE順序へ
強く依存してしまう。そこで各recordにセルIDを含め、計算結果にもIDを残した。

出力は1個のFP32値に次のように符号化した。

```text
encoded = cell_id + alive × 2048
```

hostは2048を境に生死を判定し、残ったIDを使って64×4×4の論理出力へcompactする。
同じセルを4 PEで計算するため結果も重複するが、同じIDの位置へ書き戻せばよい。
最後に全1024 IDが一度以上現れたかを確認し、欠落があれば即座にエラーにするように
した。

これはデバッグにも効いた。盤面が崩れたときに、Lifeの計算が間違っているのか、
scatter/gather後の並びが間違っているのかを切り分けやすくなったからだ。

## 8近傍の和をMAUで計算する

device kernelでは、8近傍を`f32x4x2`の8本のベクトルとして受け取り、加算を
つないで近傍数を求める。

```c
f32x4x2 neighbors = values[0] + values[1];
neighbors = neighbors + values[2];
// ... values[7]まで加算
```

同じ値を各laneへ複製しているため、ベクトルの全laneは同じ論理セルを計算する。
一見すると冗長だが、MAUのベクトル命令を確実に使い、全PEへ均等に仕事を置くための
構成である。

## Lifeの条件分岐を多項式へ置き換える

次に悩んだのがLife ruleの判定だった。device側で整数比較と複雑な分岐を組むより、
近傍数`n`と現在値`c`（0または1）から、正しい組み合わせだけ正になるscoreを
作ることにした。

```text
score = -n² - n×c + 6n + 3.5c - 8.75
```

この式は、`n = 3`または`n = 2かつc = 1`のときだけ正になる。最後に
`__builtin_frelu0x8`を使って生存値を得ることで、Life ruleをベクトルの
加算・乗算とPE命令で表現できた。

最初からこの式が自然に出てきたわけではない。必要なのは近傍数0〜8と現在値0/1の
18通りしかないため、真にしたい3点と偽にしたい残りの点を表にし、境界に余裕が
できる係数を選んだ。最終式では正しいケースのscoreが正、それ以外は負となり、
浮動小数点の境界値ちょうどを避けられている。

## hostを毎世代の検算役にする

deviceの出力がそれらしく見えるだけでは、scatter/gatherの配置ミスを見逃す可能性が
ある。そこでhostにも単純なCPU版の1 stepを実装した。

各世代では次の順序で処理する。

1. CPUで期待する次世代を計算する
2. 現在盤面を64個のhalo付きblockへpackする
3. PE recordへ展開し、deviceへwriteする
4. kernelを1回実行する
5. deviceからreadし、セルIDで論理出力へ戻す
6. CPU結果と全1024セルを比較する
7. 一致した盤面を表示し、次の世代へ進む

比較は世代、行、列を含むエラーを出すようにした。これにより、1セルでも違えば
その場で停止する。Generation 0から10まで完走し、全世代でCPU参照実装と一致した
ことで、周期境界、halo、データ配置、device計算をまとめて確認できた。

## VSMを見て「動いた」の中身を確認する

最終確認では、結果だけでなく生成されたVSMも調べた。

```sh
make vsm
grep -E 'fvadd|fvmul|frelu|l2bmi' lifegame.vsm
```

確認できた主な命令数は次のとおりだった。

```text
fvadd : 12
fvmul : 5
frelu : 1
l2bmi : 0
```

`fvadd`と`fvmul`が近傍和と多項式計算に使われ、`frelu`も出力されている。一方、
Life近傍取得のためのL1B間通信命令`l2bmi`はない。haloをhost側で作り、各PE recordを
自己完結させた設計が命令列にも反映された。

## 最後の動作確認

Docker内で次を実行し、ビルドから10世代の計算まで確認した。

```sh
make -C examples/lifegame clean run
```

Generation 0〜10が表示され、各世代のCPU照合を通過した。併せて次も確認した。

- `sample.txt`が32行で、各行32文字であること
- 存在しない入力ファイルには明確なエラーを返すこと
- 従来のaddサンプルが移動後も`1 + 2 = 3`を出すこと
- 生成物の`.bin`、`.vsm`、実行ファイルがGitの追跡対象にならないこと

## 振り返り

今回のポイントは、アルゴリズム上の配列とハードウェアへ渡す配列を分けて考えたこと
だった。論理上は64×6×6を入力し64×4×4を返す。しかし物理転送では、SDKの
scatter/gather粒度に合わせて全4096 PE用のrecordへ展開する。この二層をhost側で
明確に分離したことで、kernelは「手元のrecordを計算するだけ」という単純な形に
できた。

また、出力へセルIDを埋め込む方法と、毎世代CPU版で照合する方法は、正しい結果を
得るだけでなく、配置と計算のどちらに問題があるかを見つけるための道具になった。
MN-Core 2のようにデータ配置が計算方法そのものへ影響する環境では、最初から検算と
追跡可能性をデータ形式へ組み込むことが、結果的に最短経路だった。
